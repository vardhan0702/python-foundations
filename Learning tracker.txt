Day 18 : Prompt Engineering in Code
====================================================

1. CONCEPT
-----------
You've been sending simple questions to Claude. Today you learn to deliberately shape how Claude responds by controlling three things: the system prompt
(sets Claude's role/behavior), few-shot examples (showing Claude examples of the format you want), and temperature (controls randomness/creativity).

The system parameter is separate from your messages list — it's not a conversation turn, it's a standing instruction that applies to the entire conversation.

2. ANALOGY
----------
Think of the system prompt like the SOP (Standard Operating Procedure) document new testers receive on your team — before they ever look at a single ticket, 
they know their role, tone, and constraints. Few-shot examples are like giving a new tester 2-3 sample bug reports formatted exactly the way you want, 
so they replicate that format without being told line by line. Temperature is like telling that tester "just follow the checklist exactly" versus "use your judgment creatively."

Day 21 What is RAG? Plain English
==========================================================

RAG : Retrieval Augumented Generation.
Here it solves the most important problem.
LLM knows only the information which is trained at that cut off time. it doesn't know our own data like our company's related or project specific information.

R : Retreival -> It searches the private collection of documents which finds the most relevant pieces of text related to the user question.
Generation : These relevant pieces of information is handed over to the LLM, Now LLM has the information from both the user and from the trained data so, it gives the output relevant to the users request rather than generic output.

ANALOGY :
==============
Think of an LLM without RAG like an extremely knowledgeable consultant who’s read everything publicly available up to a certain date, but has never seen your company’s internal test case database. If you ask them “what’s TC-2847 about,” they’d have to guess or admit they don’t know.

RAG is like handing that consultant your test case spreadsheet first, flipping to the exact relevant page, and saying “read this page, then answer.” They still provide the expertise and reasoning — they just now have the right source material in front of them.



Here’s the key question: imagine your private database has 10,000 test cases stored in it. The user asks “what does TC-2847 do.” The system can’t hand all 10,000 test cases to the LLM every time — that would blow past the context window you learned about on Day 16, and cost a fortune in tokens.

So how does the system decide which handful of test cases, out of those 10,000, are actually relevant to this specific question, before handing anything to the LLM?

Embeddings — every piece of text (your test cases, and the user’s question) gets converted into a list of numbers (a “vector”) that represents its meaning, not just its exact words. Two sentences with similar meaning end up with similar numbers, even if they don’t share a single identical word.

Vector search — the database compares the question’s numbers against all 10,000 stored test cases’ numbers, and finds the ones that are mathematically “closest” in meaning. That’s your “semantic matching.”

So the full corrected flow is:

User asks a question
The question gets converted into an embedding (numbers)
The vector database (ChromaDB in your case) compares that embedding against all stored embeddings, finds the top few closest matches
Those matching chunks of text — not the whole database — get inserted into the prompt sent to the LLM
The LLM generates an answer using those specific retrieved chunks as context




1. What problem does RAG actually solve?
	Without RAG system, LLM only knows about the information on which it got trained till the cut off date. Suppose if user wants to write the functional test cases for any specific user story for a certain project, LLM do not know about the project or any existing test cases hence it will give the generic test cases instead of project specific test cases. With the RAG, LLM will come to know about the context of project and takes this as context along with the user's question and generates the response which is now enriched with the project specific data.
	
2. What is an embedding?
	Every piece of information which is our question and the context which we are going to add is gets converted into numbers (vectors) these numbers are called embeddings.
	
3. What does vector search do with those embeddings?
	Vector search typically takes the user question which is again a embedding and searches the vector db where it has closest mathematical number match and fetches the top most matching embeddings and adds along with the user specific question to enahnce the output.
	
4. Where do the retrieved chunks of text actually get placed in the API call?
	Retrieved chunks of text gets added into the user's message.

Day 23 tomorrow — Evaluation Concepts: Precision, Recall, F1
==========================================================

True positive (TP) : Predicted high priority and it is actually high priority. (correct)
False positive (FP) : Predicted high priority but it is actually NOT high priority (Incorrect)
false negative (FN) : Predicted as NOT high Priority but it is high priority (Incorrect)
true negative (TN) : Predicted as not high priority and it is NOT high priority (Correct)

Precision : TP/(TP+FP) : Of everything I predicted as high priority how much was actually correct.
Recall : TP/(TP+FN) : Of everything of actuall high priority how much did I catch.
(of all the bugs that actually exist in the system, how many did you successfully find and report?)
F1 score : balances the precision and recall into combined number.

Precision is about the accuracy of what you already flagged,
Recall is about how much of the real problem you actually uncovered, including things you might have completely missed?


def calculate_precision_recall(predicted, actual):
    true_positive = 0
    false_positive = 0
    false_negative = 0

    for item in predicted:
        if item in actual:
            true_positive += 1
        else:
            false_positive += 1

    for item in actual:
        if item not in predicted:
            false_negative += 1

    precision = true_positive / (true_positive + false_positive)
    recall = true_positive / (true_positive + false_negative)

    return {"precision": precision, "recall": recall, "tp": true_positive, "fp": false_positive, "fn": false_negative}

Day 24 tomorrow — BLEU & ROUGE: Text Quality Metrics.
==================================================
Precision, Recall, and F1 work great when you’re comparing discrete items — bug IDs, pass/fail labels, categories. But what happens when you need to evaluate generated text itself — like comparing an AI-written summary against a human-written reference summary? You can’t ask “is this bug ID correct or not.” You need to measure how similar two pieces of text are.

BLEU (originally built for translation quality) and ROUGE (originally built for summarization quality) solve this by comparing overlapping words/phrases between a generated text and a reference text.

BLEU — focuses on precision: of all the words/phrases the generated text produced, how many actually appear in the reference?
ROUGE — focuses on recall: of all the words/phrases in the reference text, how many did the generated text actually capture?

Notice — this is the same precision/recall concept from yesterday, just applied to words instead of bug IDs.

2. ANALOGY

Imagine comparing a tester’s bug report summary against your own “gold standard” summary of the same bug. BLEU asks: “of everything the tester wrote, how much matches my reference?” ROUGE asks: “of everything in my reference, how much did the tester’s version actually capture?” Same precision/recall tension as before — a tester could write a short, highly accurate summary (high BLEU, low ROUGE if they left things out) or a long, comprehensive one that includes everything but also extra fluff (high ROUGE, lower BLEU).

#Day 24 tomorrow — BLEU & ROUGE: Text Quality Metrics.

def calculate_bleu(generated, reference):
    generated_words = reference.lower().split()
    reference_words = generated.lower().split()

    generated_set = set(generated_words)
    reference_set = set(reference_words)
    overlap = generated_set.intersection(reference_set)

    precision_like_bleu = len(overlap) / len(generated_set)
    recall_like_rouge = len(overlap) / len(reference_set)

    return {"overlap_words": overlap, "precision": precision_like_bleu, "recall": recall_like_rouge}

result = calculate_bleu("The cat sat on the mat", "The cat is on the mat")
print(result)
